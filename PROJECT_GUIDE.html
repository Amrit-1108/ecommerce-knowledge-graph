GraphMind: how this project works

A plain-English guide to the e-commerce knowledge graph project: what it does, how a question travels through it, and what to say in an interview.

1What the project is, in one minute

Think of a small online shop with products, brands, vendors, customers and orders.

Normally that data sits in tables. In this project it's stored as a knowledge graph: a web of things (a product, a brand, a customer) joined by relationships ("Running Shoes is made by UrbanStep", "Order O1 was placed by Rahul").

You can ask the system a question in normal English, like "Which customers bought TechNova products?". An AI model turns the question into a search on the graph. The program runs that search and finds the matching data. The AI then writes a short answer using only the data that was found, so it can't make things up.

A web page lets you chat with it and shows the graph, lighting up the nodes used in each answer.

Simple analogy: The graph is a library. The first AI call is a helper who turns your question into an exact search slip. The Python code is the librarian who fetches only those books. The second AI call reads only those books and answers you. It isn't allowed to answer from memory.

Here is one real question followed all the way through: "Which customers bought products from TechNova?"

  1. data/ecommerce.json → graph.py · build_graph()

    Before any question: the graph is built

    When the server starts, it reads data/ecommerce.json. Every record (each product, brand, customer…) becomes a node. The file also has a relationships list, which says things like "the brand field of a Product points to a Brand, call that link MADE_BY". Those fields become edges.

    Result: 38 nodes and 65 edges held in memory by NetworkX.

  2. static/index.html → main.py · POST /ask

    The user asks a question

    The web page sends the question text to the /ask address on our FastAPI server.

  3. llm.py · question_to_query()

    LLM call #1: turn English into a graph query

    We send the AI three things: the question, the schema (which node types, properties and relationships exist, generated from the graph itself), and the rules of our small query format. We ask for JSON back, and Groq's "JSON mode" makes sure it is valid JSON.

    The AI replied with:

    {
  "find": "Customer",                          // what we want back
  "related": [{
    "path": ["PLACED_BY", "CONTAINS", "MADE_BY"], // Customer ← Order → Product → Brand
    "find": "Brand",
    "where": {"name": "TechNova"}               // ...ending at TechNova
  }]
}

    In words: "Give me customers where, if you follow placed-by → contains → made-by, you reach the brand TechNova."

  4. graph.py · run_query()

    Retrieve: Python walks the graph

    Our own code, not the AI, now looks at every node:

    • Is it a Customer? If not, skip it.
    • From this customer, follow PLACED_BY to their orders, then CONTAINS to the products in those orders, then MADE_BY to those products' brands.
    • Is one of those brands named TechNova? If yes, keep this customer.

    We found 3 customers: Rahul Sharma, Priya Nair and Sneha Reddy. For each one we also attach its direct neighbours, the TechNova node it matched, and the chain of nodes in between (its orders and products). That is the evidence.

  5. llm.py · generate_answer()

    LLM call #2: write the answer from the data only

    We send the AI the question, the query, and the retrieved data, with a strict instruction: "Answer using ONLY this data. If it isn't there, say it's not available. No outside knowledge."

    It answered: "The customers who bought products from TechNova are Rahul Sharma, Priya Nair and Sneha Reddy."

  6. static/index.html

    The web page shows it

    The page shows the answer, chips for the retrieved nodes, and the graph query (under "View graph query"). On the graph map it lights up the full chain, customers → orders → products → TechNova, and dims everything else.

The key idea to say in an interview: the AI is used twice, once to understand the question and once to phrase the answer. The actual fact-finding is done by normal, predictable Python code on the graph. That split is what keeps the answers accurate.

5Design decisions and why

Interviewers care more about why than what. These are your talking points.

Why NetworkX and not Neo4j?

The task allowed either. NetworkX runs inside Python with nothing to install, so anyone can run the project in two minutes. The dataset is small, so an in-memory graph is fast. For a real shop with millions of records, I'd move to Neo4j, a proper graph database that saves data to disk and has its own query language, Cypher.

Why does the AI write a small JSON query instead of Python code?

Safety and control. If the AI wrote Python and we ran it, a bad or tricked answer could run anything on the server. With JSON, the AI can only fill in a fixed format (find / where / related), and our own code decides what actually runs. Wrong output can at worst return no results; it can't do damage.

Why is nothing hard-coded?

The entity types, their properties and the relationships all come from the JSON file. The schema sent to the AI is generated from the graph each time. To add, say, a "Warehouse" entity, you only edit the data file: no code changes. The model, API key and file paths live in .env.

How do we stop the AI from making things up?

  • The facts come from Python code, not from the AI.
  • The answer prompt says "use ONLY this data, otherwise say it's not available".
  • We send the evidence (the matched nodes and the path to them), so the AI doesn't have to guess.
  • temperature=0, so the AI gives consistent, less "creative" output.

Why two AI calls instead of one?

One call can't both understand the question and know the data: the AI doesn't have our data until we fetch it. So the first call plans the search, our code fetches, and the second call explains the result.

Why Groq?

It offers open-source models for free with a simple API. The model name is a setting, so switching models (or providers) is easy.

6The "banana" requirement

The task said: put the word banana in the graph exactly 5 times, and make it findable through the system. It's a check that you actually loaded your own data and that retrieval works.

It appears 5 times, each in a different node:

  • Brand: Banana Leaf Organics
  • Vendor: Banana Valley Farms
  • Product: Banana Chips
  • Product: Banana Bread Mix
  • Product: Banana Smoothie Powder

How to show it: ask "Where does the word banana appear in the knowledge graph and how many times?". The AI writes a query that searches every property of every node ("any": "banana"), finds all 5, and the answer lists them with the total. You can also open /search?text=banana.

7Problems I hit and how I solved them

Great interview material: it shows you tested and debugged, not just wrote code.

1. The AI said "not available" even though the graph found the right answer

For "customers who bought TechNova", the graph correctly found 3 customers. But the AI only saw each customer and their orders. It couldn't see the link to TechNova, so it (correctly!) refused to claim it. Fix: retrieval now attaches the evidence, meaning the TechNova node that matched and the chain of orders and products in between. The answer became correct, and it also let the UI light up the full path.

2. Rate limit on the free tier

Groq's free plan allows about 8,000 tokens per minute. Running all samples quickly hit that limit. Fix: made the data sent to the AI more compact, added automatic retries, and a short pause between sample questions.

3. The model was removed

The first model we picked (Llama 3.3) was no longer on Groq. Because the model name is a setting in .env, switching to openai/gpt-oss-120b took one line. That's a good example of why nothing should be hard-coded.

4. A question the query format can't express

"Orders that are pending or shipped" needs an OR, which the simple format doesn't support. I kept the format simple and chose sample questions it can handle. This is listed under limitations.

8Limitations and how I'd improve it

Being honest about limits looks mature in an interview.

LimitationHow to improve
The query format has no OR, counting or sorting; the AI does simple maths itself from the data.Add operators like "or", "count", "sort", or move to Neo4j + Cypher, which has all of these.
The graph lives in memory and is rebuilt from a file.Use a real graph database (Neo4j) for large or changing data.
Every query scans all nodes. That's fine for 38, slow for millions.Indexes by type and name, or a graph database.
Names must roughly match ("TechNova"). A typo like "Tek Nova" finds nothing.Fuzzy matching or embeddings (meaning-based search) to find the closest names.
No memory between questions ("what about their orders?").Send recent chat history to the AI.
The AI's query isn't checked against the schema before running.Validate it, and ask the AI to retry if it uses an unknown type or relationship.
No login or automated tests.Add authentication and unit tests for graph.py.

9Likely interview questions (click to see an answer)

Walk me through your project.

"I built a knowledge graph of an e-commerce store, with products, brands, categories, vendors, customers and orders, using NetworkX. A user asks a question in English. An LLM on Groq converts it into a small JSON graph query. My Python code runs that query on the graph and collects the matching nodes with evidence. A second LLM call writes the answer using only that data. It's served with FastAPI and has a web UI that highlights the used nodes on a graph map."

What is a knowledge graph, and why use one instead of tables?

It stores data as entities connected by named relationships. It's great when questions are about connections, like "customers who bought products of brand X supplied by vendor Y". In tables that needs several joins. In a graph you just follow the links.

How does the LLM know what's in your graph?

I send it the schema, a list of node types, their properties and the relationships. It's generated automatically from the graph, so if the data changes, the AI's view updates too. I never send the whole dataset in that first call, only the structure.

How do you make sure answers only come from the graph?

Retrieval is done by my code, not the AI. The answering prompt tells the AI to use only the supplied data and to say "not available" otherwise. I pass the matched evidence, and use temperature 0. I tested it: when evidence was missing, the AI said "not available" instead of guessing.

What happens if the LLM returns a bad query?

If it isn't valid JSON, the API returns a clear error. If it's valid but uses the wrong names, the query simply finds nothing and the AI says the information isn't available. Because it's JSON and not code, a bad query can't harm the system. An improvement would be validating it against the schema and retrying.

Why not let the LLM write Cypher or Python directly?

Running AI-written code is a security risk (someone could trick it into writing harmful code). A fixed JSON format limits the AI to safe operations. With Neo4j, Cypher would be natural, and I'd run it with read-only permissions.

How does the "path" in a query work?

It's a list of relationship names to follow in order. From a customer, ["PLACED_BY", "CONTAINS", "MADE_BY"] goes customer → their orders → products in those orders → those products' brands. The code follows each link in either direction, so the AI doesn't need to know which way an arrow points.

How would this scale to millions of products?

Move the graph to Neo4j (on disk, indexed, with Cypher). Add indexes on names. Cap the number of results sent to the AI so prompts stay small. Cache common questions. The overall flow stays the same; only the storage and query engine change.

What is RAG, and is this RAG?

RAG means "retrieve first, then generate", so the AI answers from real, fetched data. Yes, this is Graph RAG: the retrieval step is a graph search instead of a document or vector search.

How did you satisfy the banana requirement?

"Banana" appears exactly 5 times, in 1 brand, 1 vendor and 3 product names, each in a separate node. The query language has an "any" field that searches all properties, so asking where banana appears returns all 5. There's also a /search endpoint.

What was the hardest bug?

The "TechNova customers" case. Retrieval was right, but the AI couldn't see why those customers matched, so it refused to answer. I fixed it by sending evidence: the matched brand and the path of orders and products. It taught me that grounding needs the proof, not just the result.

Why FastAPI?

It's simple, fast, and gives automatic request checking and an interactive docs page at /docs, which is handy for testing and demos.

What would you add with more time?

Neo4j backend, query validation with retry, fuzzy name matching, chat memory for follow-up questions, automated tests, and an evaluation set of questions with expected answers to measure accuracy.
